# Чернетки відповідей для підтримки

Сервіс приймає звернення від хелпдеску, знаходить статті в базі знань, просить LLM (Claude) написати чернетку відповіді з посиланнями на них і показує її оператору. Після підтвердження відповідь надсилається клієнту через API хелпдеску.

Стек: Python 3.13, FastAPI, PostgreSQL 17, Anthropic SDK, Jinja2. Черга задач, лімітер запитів до LLM і дедуплікація зроблені на Postgres, без Redis чи Celery.

## Публічне розгортання

Сервіс розгорнуто на Railway:

| Що | Адреса |
|---|---|
| Інтерфейс оператора (пароль у супровідному листі, логін будь-який) | https://support-drafts-production.up.railway.app/ |
| Вебхук | `POST https://support-drafts-production.up.railway.app/webhooks/helpdesk` |
| Health check | https://support-drafts-production.up.railway.app/health |
| Що отримав мок хелпдеску | https://support-drafts-production.up.railway.app/mock-helpdesk/replies |

Звернення для перевірки (`reply_url` веде на мок на тому самому домені):

```bash
curl -X POST https://support-drafts-production.up.railway.app/webhooks/helpdesk -H 'Content-Type: application/json' -d '{
  "event_id": "evt_demo_1",
  "ticket_id": "T-1042",
  "customer_email": "user@example.com",
  "message": "Не можу експортувати звіт у PDF",
  "reply_url": "https://support-drafts-production.up.railway.app/mock-helpdesk/tickets/T-1042/replies"
}'
```

Кожен `event_id` приймається один раз, тож для нового звернення змініть його.

## Запуск

Потрібні Docker і Docker Compose.

```bash
cp .env.example .env
```

У `.env` можна вписати `ANTHROPIC_API_KEY`. Без нього сервіс теж працює: він робить справжній запит до Anthropic, отримує 401 і підставляє статичну відповідь через 5–30 секунд, як після справжнього виклику. Файл `.env` необов'язковий: без нього діють значення за замовчуванням.

```bash
docker compose up --build
```

Піднімаються три контейнери: `db` (Postgres), `app` (HTTP: вебхук, інтерфейс оператора, мок хелпдеску) і `worker` (генерація чернеток і надсилання відповідей). Схема БД створюється автоматично при старті.

| Що | Адреса |
|---|---|
| Інтерфейс оператора | http://localhost:8000/ |
| Вебхук | `POST http://localhost:8000/webhooks/helpdesk` |
| Health check | http://localhost:8000/health → `200 OK` |
| Що отримав мок хелпдеску | http://localhost:8000/mock-helpdesk/replies |
| Статті бази знань | http://localhost:8000/kb/export-pdf |
| OpenAPI | http://localhost:8000/docs |

## Як перевірити вручну

1. Надішліть звернення. `reply_url` веде на мок хелпдеску. Адреса `app` резолвиться всередині мережі compose, звідки воркер і надсилає відповідь.

   ```bash
   curl -X POST localhost:8000/webhooks/helpdesk -H 'Content-Type: application/json' -d '{
     "event_id": "evt_8f2a",
     "ticket_id": "T-1042",
     "customer_email": "user@example.com",
     "message": "Не можу експортувати звіт у PDF",
     "reply_url": "http://app:8000/mock-helpdesk/tickets/T-1042/replies"
   }'
   ```

   Відповідь: `{"status":"accepted"}`. Якщо надіслати те саме ще раз, прийде `{"status":"duplicate"}` і новий запис не з'явиться.

2. Відкрийте http://localhost:8000/. Через 5–30 секунд оновіть сторінку: у звернення з'явиться чернетка зі списком статей.
3. Натисніть «Підтвердити». Воркер надішле відповідь на `reply_url`. Мок навмисно повертає 503 у 20% випадків, тож іноді видно повторну спробу й текст помилки. Ще у 10% випадків мок зберігає відповідь, але відповідає вже після таймауту воркера. Тоді звернення отримує статус `unconfirmed`, і оператор вирішує сам: «Дійшла» або «Не дійшла, надіслати ще раз» (див. нижче).
4. На http://localhost:8000/mock-helpdesk/replies видно, що отримав «хелпдеск». Якщо оператор помилково натисне «надіслати ще раз», хоча відповідь уже дійшла, мок розпізнає повтор за `Idempotency-Key`: `deliveries` стане 2, а дубль клієнт не побачить.

## Як це влаштовано

```
Хелпдеск ──POST /webhooks/helpdesk──▶ app ──INSERT──▶ Postgres (tickets)
                                                          ▲   │
                         оператор ──Підтвердити──▶ app ───┘   │ claim (SKIP LOCKED + lease)
                                                              ▼
                                   Claude API ◀── worker ──▶ POST reply_url (Idempotency-Key)
```

Таблиця `tickets` одночасно є і даними, і чергою:

```
new          ──(чернетка готова)──────────────────▶ draft
draft        ──(оператор: «Підтвердити»)──────────▶ approved
draft        ──(оператор: «Відхилити»)────────────▶ rejected
approved     ──(хелпдеск 2xx)─────────────────────▶ sent
approved     ──(усе, крім «не з'єдналось» і 5xx)───▶ unconfirmed
approved     ──(воркер упав посеред надсилання)───▶ unconfirmed
unconfirmed  ──(оператор: «Дійшла»)───────────────▶ sent
unconfirmed  ──(оператор: «надіслати ще раз»)─────▶ approved
new/approved ──(MAX_ATTEMPTS невдалих спроб)──────▶ failed
```

### Вимоги та рішення

| Вимога | Рішення |
|---|---|
| Хелпдеск чекає ≤ 2 с, а LLM відповідає 5–30 с | Вебхук лише валідує тіло, робить один `INSERT` і відповідає. Генерацію виконує окремий процес `worker`. |
| Та сама подія приходить кілька разів, зокрема одночасно | `event_id` має `UNIQUE`, запис іде через `INSERT … ON CONFLICT DO NOTHING`. Перевірки «чи вже є» немає, тож гонки теж. На дублікат вебхук відповідає 200, щоб хелпдеск припинив повтори. |
| Звернення не можна втрачати | 200 повертається тільки після коміту в Postgres. Якщо БД недоступна, хелпдеск отримує 5xx і повторить запит. Воркер бере задачу в «оренду» (`locked_until`, 5 хв): якщо він упав посеред роботи, оренда спливає і задачу підхоплює інший воркер. |
| До 500 звернень за 10 хвилин | Черга згладжує пік. Воркер обробляє до `WORKER_CONCURRENCY` (30) задач одночасно. Цього вистачає, щоб тримати 60 запитів/хв при 30 с на виклик. |
| 60 запитів до LLM на хвилину на весь сервіс | Ковзне вікно в таблиці `llm_calls` під `pg_advisory_xact_lock`. Ліміт спільний для всіх процесів воркера. Повтори SDK вимкнено (`max_retries=0`), тому кожна спроба проходить через лімітер. |
| Хелпдеск повертає 5xx або не відповідає вчасно | Автоматично повторюються лише випадки, коли відповідь точно не збережена: не вдалося з'єднатися, 5xx або 429. Повтор іде з експоненційною затримкою (10 с … 10 хв), до `MAX_ATTEMPTS` спроб, далі статус `failed`. Усе інше (таймаут, обрив, 4xx, незрозуміла відповідь, помилка нашої БД після запиту) автоматично не повторюється: статус `unconfirmed`, вирішує оператор (див. наступний рядок). |
| Клієнт не має отримати ту саму відповідь двічі | 1) Переходи станів атомарні (`UPDATE … WHERE status = '<очікуваний>'`), тож подвійний клік чи два оператори не створять другого надсилання. 2) Якщо відповідь могла дійти, сервіс сам її не повторює: оператор перевіряє хелпдеск і тисне «Дійшла» або «надіслати ще раз». Це стосується і падіння воркера посеред надсилання: звернення `approved` зі спливлою орендою не забирається на повтор, а переходить в `unconfirmed`. 3) Кожен запит несе `Idempotency-Key: reply-<id>`, однаковий для всіх спроб. Якщо хелпдеск його підтримує (мок підтримує), навіть помилковий повтор не дасть дубля. |
| Режим без API-ключа | Запит до Anthropic відправляється з ключем-заглушкою і отримує 401. Після цього береться статична відповідь із затримкою 5–30 с. Решта конвеєра (лімітер, черга, статуси, модерація) не знає, що відповідь статична. |

**Чому так.** Після таймауту неможливо дізнатися, чи дійшла відповідь, тому є лише вибір між «можливий дубль» і «можлива втрата». Завдання прямо забороняє дубль, а API хелпдеску не обіцяє ідемпотентності. Тому сервіс не вгадує, а передає рішення людині: відповідь не губиться (вона видна в інтерфейсі) і не дублюється автоматично. 5xx вважається відмовою, тобто відповідь не прийнято, і повторюється, так само 429 (хелпдеск відмовив через ліміт). Якщо конкретний хелпдеск на 5xx усе ж зберігає відповідь, такі випадки теж варто віддавати оператору.

### LLM

- Модель `claude-opus-5-5` (змінюється через `LLM_MODEL`), Anthropic Python SDK.
- Увімкнено server-side `fallbacks: "default"`: якщо класифікатор безпеки відхилить запит, API сам повторить його на резервній моделі. Відповідь зі `stop_reason: "refusal"` вважається помилкою і йде на повтор.
- Текст клієнта передається в тегах `<message>`, а системний промпт каже вважати його даними, а не інструкціями. Остаточний захист від prompt injection — людина, яка модерує чернетку.
- Список «Корисні статті» додає сам сервіс, а не модель. Тому посилання завжди ведуть на справжні статті, навіть зі статичною відповіддю.

### База знань

8 статей про вигаданий сервіс аналітики «Звітко» у `kb/*.md`, згенеровані AI. Вони завантажуються в пам'ять при старті. Пошук рахує збіги слів за 4-літерним префіксом (грубий стемінг для української), а збіги в заголовку мають подвійну вагу. Для 5–10 статей цього вистачає. Для великої бази варто перейти на ембеддинги в pgvector.

## Налаштування

Усі змінні описані в [.env.example](.env.example).

| Змінна | За замовчуванням | Що робить |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | Без ключа діє режим статичних відповідей |
| `LLM_MODEL` | `claude-opus-5-5` | Модель Claude |
| `LLM_RPM` | `60` | Ліміт запитів до LLM на хвилину на весь сервіс |
| `WORKER_CONCURRENCY` | `30` | Скільки задач один воркер обробляє паралельно |
| `MAX_ATTEMPTS` | `8` | Після стількох невдалих спроб статус стає `failed` |
| `PUBLIC_BASE_URL` | `http://localhost:8000` | База для посилань на статті в чернетках |
| `OPERATOR_PASSWORD` | — | Якщо задано, інтерфейс оператора і список відповідей мока закриваються HTTP Basic Auth (логін будь-який) |
| `REPLY_URL_HOSTS` | `helpdesk.example.com` | Хости хелпдеску, на які дозволено надсилати відповіді (`reply_url`). На власний хост сервісу (`app` і хост з `PUBLIC_BASE_URL`) можна лише за шляхом `/mock-helpdesk/…`, бо там же живе інтерфейс оператора |
| `MOCK_FAIL_RATE` / `MOCK_SLOW_RATE` | `0.2` / `0.1` | Як часто мок хелпдеску повертає 503 і як часто відповідає із запізненням |

## Навантаження

Заміри на ноутбуці (4 ядра; клієнт, сервіс і Postgres на одній машині):
- 500 вебхуків за 30 секунд, що у 20 разів щільніше за пік із завдання: p99 71 мс;
- 500 вебхуків одночасно: усі прийняті без втрат, але p99 близько 7 с. Один процес uvicorn обробляє приблизно 70 запитів/с. Для таких сплесків варто запустити кілька процесів (`uvicorn --workers N`).

## Деплой

Розгорнуто на Railway з GitHub-репозиторію. Так само підійде будь-який хостинг, що вміє запускати Docker і має керований Postgres:
- PostgreSQL: керована база Railway;
- сервіс `app`: образ з `Dockerfile`, команда за замовчуванням, публічний домен на порт 8000; змінні `DATABASE_URL=${{Postgres.DATABASE_URL}}`, `PUBLIC_BASE_URL=https://<домен>` (зі схемою), `OPERATOR_PASSWORD`, `PORT=8000`;
- сервіс `worker`: той самий репозиторій, команда запуску `python -m app.worker`, без домену; змінні `DATABASE_URL` і `PUBLIC_BASE_URL`;
- за бажанням `ANTHROPIC_API_KEY` сервісу `worker` (LLM викликає лише він). Без ключа працює режим статичних відповідей.

Для тесту на задеплоєному сервісі в `reply_url` вказуйте `https://<домен>/mock-helpdesk/tickets/<id>/replies`. Для справжнього хелпдеску додайте його домен у `REPLY_URL_HOSTS`.

## Чого немає і що зробив би далі

- **Перевірки підпису вебхука.** Завдання не описує механізм, але в продакшні потрібен HMAC-підпис від хелпдеску.
- **Редагування чернетки оператором і повторного запуску `failed`-звернень з інтерфейсу.** Завдання цього не вимагає.
- **Пагінації та фільтрів в інтерфейсі.** Показуються останні 200 звернень, спершу ті, що чекають модерації.
- **Інструменту міграцій.** Схема створюється через `CREATE … IF NOT EXISTS`. Наступну зміну схеми варто робити вже через Alembic.
- **Плавної зупинки воркера.** Після `SIGTERM` генерації, що виконувалися, повертаються в чергу, коли спливе оренда (до 5 хв). Надсилання, що виконувалися, через ту саму оренду йдуть в `unconfirmed` до оператора.

## Робота з AI

Сервіс написано в Claude Code, історію комітів залишено як є.
- [CLAUDE.md](CLAUDE.md) — карта коду і інваріанти, які агент не має права ламати (дедуплікація, атомарні переходи статусів, правило «не надсилати двічі»).
- [.claude/agents/reviewer.md](.claude/agents/reviewer.md) — субагент, що перед комітом перевіряє диф проти цих інваріантів. Він знайшов дубль відповіді після падіння воркера посеред надсилання і можливість націлити `reply_url` на власні ендпоінти оператора (виправлено в `ba463b0`, `2008afa`).
- Твердження агента «працює» перевірялись запуском: тести, `scripts/e2e.sh`, заміри навантаження. Наприклад, агент пояснив p99 ≈ 7 с при 500 одночасних вебхуках замалим пулом з'єднань; повторний замір це спростував, тому в розділі «Навантаження» записано реальну межу, а не «виправлено».
