# Як велася робота з AI-агентом

Сервіс написано в Claude Code. Тут — як була побудована робота, що з налаштувань агента лежить у репозиторії і де вивід агента перевіряли й виправляли. Історія комітів не стискалась, тож усе нижче можна звірити з `git log`.

## Процес

1. **Розбір задачі до коду.** Агент прочитав PDF і розклав його на вимоги та «пастки»: таймаут 2 с проти LLM на 30 с, одночасні дублікати, глобальний ліміт 60/хв, неоднозначний таймаут при надсиланні, режим без ключа, який все одно робить справжній запит. Архітектуру (черга в Postgres, оренда задач, ковзне вікно для ліміту) обрано на цьому етапі, до першого рядка коду.
2. **Вертикальні зрізи.** Кожен коміт — робочий шматок, перевірений наживо перед комітом: каркас і база знань → вебхук і схема → воркер → UI → тести й документація.
3. **Перевірка, а не довіра.** Кожне твердження агента про те, що «працює», підтверджувалось запуском: curl, логи воркера, запити до БД, навантажувальний тест, браузер. Нижче — випадки, де перевірка щось знайшла.
4. **Окреме рев'ю.** Після «готово» проєкт перечитано очима рев'юера: вимоги по одній, потім пошук підозрілих місць. Знайдені проблеми виправлено окремим комітом.
5. **Специфікація.** `docs/spec.md` написано після рев'ю, а не до коду: вимоги з PDF стали перевірюваними критеріями з ідентифікаторами, кожна прив'язана до коду і доказу. Тепер це контракт для наступних змін.

## Налаштування агента в репозиторії

| Файл | Навіщо |
|---|---|
| [CLAUDE.md](../CLAUDE.md) | Карта коду, **інваріанти** (що не можна ламати і чому), конвенції, команди. Інваріанти — головне: це те, що агент найімовірніше зламав би «оптимізацією» |
| [AGENTS.md](../AGENTS.md) | Посилання на `CLAUDE.md`, щоб Codex і Cursor читали ті самі правила |
| [docs/spec.md](spec.md) | Вимоги R1–R20, S1–S3 і припущення A1–A8 з критеріями та доказами |
| [.claude/skills/verify](../.claude/skills/verify/SKILL.md) | `/verify`: стек, тести і e2e-сценарій. «Готово» означає, що три кроки пройшли, а не що код виглядає правильно |
| [.claude/agents/reviewer.md](../.claude/agents/reviewer.md) | Субагент-рев'юер лише на читання. Перевіряє диф проти інваріантів і специфікації, шукає гонки й дірки на межах довіри |
| [.claude/settings.json](../.claude/settings.json) | Дозволи: рутинні команди без запитів; заборона читати `.env` (секрети не потрапляють у контекст агента) і `down -v` (знищує дані). Stop-хук |
| [.claude/hooks/tests-on-stop.sh](../.claude/hooks/tests-on-stop.sh) | Агент не може завершити хід із червоними тестами, якщо чіпав код: хук запускає тести і повертає агенту помилку |
| [scripts/e2e.sh](../scripts/e2e.sh) | Сценарій з README як скрипт: дублікати, allowlist, чернетка, підтвердження, доставка рівно один раз |

Під час роботи також використовувались: плагін «ponytail» (найменша повна зміна, без коду «на майбутнє»), скіл `claude-api` (актуальні ID моделей і параметри SDK замість пам'яті моделі), вбудований браузер (перевірка UI).

## Що агенту не довіряли

- Твердження «працює» без запуску. Звідси `/verify` і Stop-хук.
- Назви моделей і параметри SDK з пам'яті. Їх брали зі скілу `claude-api` і перевіряли інспекцією встановленого SDK (`fallbacks="default"` є в типах SDK 2.5).
- Власні тести агента. Ключову поведінку ламали навмисно й дивились, чи тест це ловить: автоматичний повтор після таймауту, вебхук без `ON CONFLICT`, вимкнений allowlist `reply_url`, а після рев'ю ще прибирали перевірку спливлої оренди, захист статусів, перевірку `Origin` і обмеження шляху для власного хоста. Двічі тест поломку не впіймав (захист статусів, застарілий воркер) — обидва тести переписано, а мутацію тепер роблять видаленням умови, а не заміною, щоб не зламати сам SQL. Stop-хук теж перевірено: він сам заблокував завершення ходу, поки в коді був підкинутий для рев'юера баг.
- Власне рев'ю агента-автора. Після «готово» диф перевіряє окремий субагент `reviewer`, який цей код не писав.
- Висновки з одного заміру. Див. історію з пулом з'єднань.
