# Специфікація

Вимоги тестового завдання, переписані як перевірювані критерії. Кожна вимога має ідентифікатор, місце в коді і доказ: автотест з `tests/test_service.py`, крок у `scripts/e2e.sh` або вимір. Цей файл — контракт для агента: зміна поведінки починається зі зміни тут.

Рішення і трейдофи описані в README, розділ «Вимоги та рішення». Тут — лише що саме має виконуватися і як це перевірено.

## Припущення

Завдання цього не визначає, тому рішення прийнято тут. Якщо хелпдеск поводиться інакше, міняти треба відповідний рядок.

| ID | Питання | Припущення |
|---|---|---|
| A1 | Чи ідемпотентний API відповідей хелпдеску? | Невідомо. Тому таймаут не повторюється автоматично (R11), а `Idempotency-Key` додається на випадок, якщо хелпдеск його підтримує |
| A2 | Чи означає 5xx, що відповідь не збережена? | Так, 5xx вважається відмовою і повторюється. Якщо це не так, 5xx теж треба віддавати в `unconfirmed` |
| A3 | Кілька подій для одного `ticket_id` | Кожна подія — окреме звернення з окремою чернеткою |
| A4 | Що після «Відхилити»? | Звернення закривається без відповіді. Повторна генерація чи ручна відповідь — поза обсягом |
| A5 | Підпис вебхука | Не описаний у завданні, тому не перевіряється. У продакшні потрібен HMAC |
| A6 | «Статична відповідь» у режимі без ключа | Статичний текст LLM. Список статей додає сервіс, тож посилання все одно справжні |
| A7 | 4xx у відповідь на надсилання | Хелпдеск відмовив або (409) вже має цю відповідь. Не повторюється автоматично, йде в `unconfirmed` до оператора. Виняток — 429: запит відхилено до збереження, повторюється як 5xx |
| A8 | Два оператори з різними версіями сторінки тиснуть «надіслати ще раз» | Друге натискання спрацює, якщо між ними надсилання знову закінчилось `unconfirmed`. Ризик прийнято: кожне натискання — рішення людини після перевірки хелпдеску |
